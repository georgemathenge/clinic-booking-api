## 2. One example where an AI suggestion improved my work

- **Prompt:** [paste or paraphrase what you asked, e.g. "help me build this clinic booking assessment" and then the follow-up about double-booking]
- **What it suggested:** enforce "one active booking per slot" with a Postgres **partial unique index** (`UNIQUE (doctor_id, start_time) WHERE status = 'booked'`) instead of only checking in code first. Translate the resulting `IntegrityError` into a `409`.
- **Why it was better:** my instinct would have been [describe: e.g. query for an existing booking, then insert]. That approach has a race condition under concurrent requests. The index makes the guarantee atomic, and because the condition only covers booked rows, cancelled appointments can stay in the table for history without blocking the slot.

## 3. One example where AI output was wrong or incomplete, and how it was caught

- **The concurrency test proved nothing at first.** The first version of `test_concurrent_bookings_only_one_wins` raced two threads through the normal booking path, and it passed. To check that it was actually testing the database guarantee, the unique index was temporarily removed from the model and the test re-run. **It still passed** three times out of three: the threads never overlapped inside the check-then-insert window, so the app-level check was catching the duplicate every time. The test was rewritten to disable the app-level check (forcing the worst-case interleaving). It now **fails without the index and passes with it**.
  Lesson: a passing test isn't evidence until you've seen it fail for the right reason.
