# Section 4 — AI Reflection

I built this assessment with **Claude Code** (Anthropic's coding agent) working in my terminal. I used it heavily, and I'm being upfront about that because the brief asks for honesty.

## 1. What I used AI for across the four sections

- **Getting started:** I gave Claude Code the assessment PDF and asked it to help me build the project. It summarised the requirements and flagged the main technical risk (double-booking under concurrent requests). It then gave me options for framework, database, hosting and project location, and I chose FastAPI, PostgreSQL and Render.
- **Section 1 (design):** it proposed the data model (doctors, weekly working-hour blocks, patients, appointments). It also proposed computing slots on the fly instead of storing them, and enforcing "one booking per slot" in the database. It drafted the design section of the README, including the trade-offs and assumptions.
- **Section 2 (API):** it wrote most of the code: models, the service layer, routers, error handling, Alembic migrations (including seed data for the 5 doctors) and the 38 tests. It also ran the tests and smoke-tested the endpoints with curl against the app running in Docker.
- **Section 3 (deployment):** it wrote the Dockerfile, `render.yaml` and the GitHub Actions workflow. It also created the GitHub repo, set the deploy-hook secret, turned on branch protection, and opened and merged the first PR to prove the pipeline. I did the Render setup myself in the browser: I connected the repo, created the Blueprint, checked the first deploy, and gave it the service URL and deploy hook.
- **Section 4:** I asked it to help write this reflection from what actually happened in the session.

## 2. One example where an AI suggestion improved my work

- **Prompt:** I gave it the PDF with *"hey so i am to do this project, you can help me"* and then picked the stack it offered.
- **Suggestion:** don't only check "is this slot free?" in code before inserting. Two requests at the same moment can both pass that check and both book. Instead, put a **partial unique index** on `(doctor_id, start_time) WHERE status = 'booked'`, so the database itself rejects the second booking, and turn that rejection into a `409 SLOT_TAKEN`.
- **Why it improved things:** a check-then-insert in code is the obvious way to do it, and it has that race. The index makes the guarantee atomic. Because it only covers *booked* rows, cancelled appointments stay in the table as history without blocking the slot. The same idea stops a patient booking two doctors at the same time.

## 3. One example where AI output was wrong or incomplete, and how it was caught

- **The concurrency test didn't test anything at first.** The AI's first version raced two threads to book the same slot, and it passed. To check that it was really testing the database guarantee, the unique index was temporarily removed and the test re-run. **It still passed**, three times out of three: the threads never overlapped in the window that matters, so the normal code check caught the duplicate every time. The test was rewritten to switch off the code-level check and force the worst case. It now **fails without the index and passes with it.**
  What I took from this: a passing test means nothing until you've seen it fail for the right reason.
- **The deploy health check was too weak.** The first pipeline accepted any `200` from `/health` after triggering a deploy. But the *old* version keeps answering `200` until Render swaps it out, so the check could pass before the new code was live. This was caught while planning the first PR and fixed in PR #1: `/health` now reports the deployed git commit, and the pipeline waits until it matches the merged commit. On the first real deploy, the old version kept answering for four attempts before the new commit showed up, which confirmed the fix was needed.
- **Smaller ones:** Alembic's autogenerated migration didn't drop the enum type on downgrade (caught by running down and then up again). The Alembic config also couldn't find the `app` package at first (caught when the command failed).

## 4. Two decisions I made without AI

Honestly, most of the technical decisions were proposed by the AI and approved by me. Two calls were mine:

1. **Choosing the stack and the hosting from the options it gave me.** It laid out FastAPI, Django REST and Go, Postgres or SQLite, and Render, Fly.io, Railway or AWS/GCP. I picked FastAPI + Postgres + Render because of the 3–5 day deadline. I wanted the setup I could get running, deployed and understood fastest, rather than the most impressive one. Render especially let me get a public URL with a managed database without a card or a lot of infrastructure work.
2. **Doing the hosting setup myself, and prioritising submitting on time.** I created the Render service in my own account, checked the live deployment, and handed over only the URL and deploy hook. With the deadline close, I chose to submit a working, deployed and tested system with a clear README rather than keep adding features. I trusted my own judgement here because these were decisions about my accounts, my time and my submission, not technical questions with an answer the AI could look up.

**What I'd do differently:** go through the design myself before letting the AI write code, so that more of the decisions above come from me and not from approving its suggestions.
